# Isolated profile storage prototype

Not connected to the game, JavaScriptBridge, `user://`, the existing journey save,
Pages deployment, or any real player's profile. Unlock identifiers have no game
effects. Existing saves without a native run ID are not imported for rewards.

## Concrete Web implementation

`profile_storage.js` uses an independent, prefix-restricted IndexedDB database
with `profiles`, `receipts`, `runs`, and one global `slots/active` record.

- `claimWriter(owner, leaseMs)` / `renewWriter(auth, leaseMs)` return an expiring
  global fencing token and expected active-slot revision. Renewal cannot silently
  reclaim an expired token. A second active owner gets `WRITER_BUSY`.
- `createRun(auth, snapshot, replaceActive=false)` compares slot revision inside
  the transaction; explicit replacement abandons the prior active run. It cannot
  overwrite another tab's new run using stale credentials. IDs are newly generated
  UUIDs, not IDs backfilled onto historical saves.
- `saveRun(id, auth, expectedRunRevision, snapshot)` checks global fence, lease,
  active pointer and run revision in one transaction. An old tab cannot overwrite
  a newer run or old autosave revision.
- `settleRun(id, auth, expectedRunRevision, outcome)` reads the stored snapshot.
  It derives maximum floor from its continuous `floor_seen` prefix, not from a
  caller-provided score. Victory requires saved `won` and the matching chapter.
  It atomically commits the profile ledger, indexed receipt, archived run and
  slot revision. Same-ID/same-summary returns the original receipt; conflicting
  summaries never overwrite it. All successful writes resolve on transaction
  **completion**, not an individual put callback.
- Profile schema and pure settlement match `scripts/legacy_profile.gd`; an
  envelope `commitRevision` is distinct from profile format `revision=1`.
  Strict validation includes exact fields, receipt union, unlock IDs and duplicate
  grants. Missing profile with existing receipts is corruption, not a new profile.
- Limits: 4096 runs and 4096 receipts, at most 1 MiB per snapshot. Full stores reject
  writes without pruning receipts. Native prototype may have an additional total
  file-size limit appropriate to its single-file implementation.

The prototype's snapshot is intentionally a stub: `seed_value`, `floor_seen`,
`floor`, `hp`, `moves`, `won`. A future game adapter must obtain it from a validated
World save, never a user-editable UI score. This is transactional consistency,
not anti-cheat against editing all local data. Clearing browser storage, disk
failure and whole-profile backup rollback remain outside the promise.

## Godot integration proposal, not implemented

A small JavaScriptBridge adapter could call these async operations and return a
request ID plus completion callback to Godot. Pending UI must remain pending until
`tx.oncomplete`; rejected/quota/aborted transactions must not display a reward.
Do not implement profile transactions as independent Godot FileAccess writes to
IDBFS files. Gameplay should have one acknowledged global writer; background tabs
whose lease expires must stop writes until an explicit reload/reclaim action.
Undo changes only the active run snapshot. Once a receipt commits, that run is
archived and cannot be reactivated by loading an earlier gameplay snapshot.

## Reproducible tests

`node tools/test_profile_vectors.mjs` compares all stable fields and input purity
against vectors generated by the actual GDScript pure ledger. This does not test
IndexedDB or browser persistence.

Serve `tools/` over localhost and open `profile_storage_harness.html` in Chromium.
The self-test button creates its own random test database; it exercises real
IndexedDB connections, every injected transaction-abort boundary, compare-and-swap
races, finite milestones, malformed profile rejection, lease takeover and reopen.
It never clears a database. Test databases deliberately remain for inspection.

For real two-tab testing, use the exact same origin and `?db=` parameter in both
pages. A claims the global writer and creates a run. B cannot claim while the
lease is alive. After A explicitly shortens its lease and it expires, B claims a
higher fence. A's save **and new-run creation** must fail. B reads the current run,
tries `after_profile` abort and verifies all stores unchanged, then settles and
retries. Close/reopen a page and verify archived run and original receipt survive.
The page provides actual buttons for all writes; browser inspection does not need
to execute write APIs from developer evaluation.

Controlled aborts model logical transaction failure, not a measured browser
process-kill/power-loss event. Real browser results must be recorded separately;
passing pure Node tests is not evidence that this Web storage path works.

## Recorded verification (2026-11-08)

Native Chrome UI QA opened two real same-origin tabs at
`http://127.0.0.1:8765/profile_storage_harness.html` using database
`magic-tower-profile-harness-v2-native-qa18`. The page's independent random-DB
self-test reported **24 passing checks**. Manual two-tab actions verified:

- busy writer rejection and stale run-revision CAS rejection;
- expired-lease takeover to fence 2, rejecting the old tab's saves **and create**;
- controlled `after_profile` abort left profile/receipt/run/slot unchanged;
- successful settlement, duplicate returning the same receipt, and a second run
  granting no repeated 3/5/8 milestone;
- closing tab A and reloading B preserved archived state and receipts.

These tests use explicitly simulated snapshots, not a live Godot game or its
current save file. Injected transaction aborts are not actual browser-process
kills or power-loss testing. No production persistence claim follows from them.
The DB remains available for inspection; the harness has no clear-data control.

The pure cross-language Node test independently passed all **37 GDScript-generated
cases / 259 comparisons**, then **10 added counter-boundary checks** (269 total).
Every increment of writer fence, slot revision, run revision and storage commit
revision now uses `nextCounter`: `MAX_SAFE_INTEGER` and invalid values throw
`COUNTER_EXHAUSTED`. Inside an IndexedDB transaction that error aborts every write,
including a preceding tentative run insertion or archive update. No wraparound or
unsafe integer is committed. This boundary addition does not change the already
tested normal UI operations; its new boundary checks are pure tests.

## Exact JavaScript return protocol (not interchangeable with native wrappers)

All persistence methods return Promises. Argument validation may also throw before
a Promise is created, so an adapter must catch both synchronous and async errors.
`StorageFault` provides `code`; actual IndexedDB failures may be DOMExceptions
with `name` instead. A future bridge should normalize these explicitly.

| API | Success value |
| --- | --- |
| `ProfileStorage.open(databaseName)` | `ProfileStorage` instance |
| `readSlot()` | `{id:'active', revision, activeRunId, lastFence, writer}`; fresh virtual slot if genuinely empty |
| `claimWriter(owner, leaseMs)` / `renewWriter(auth, leaseMs)` | `{owner, fence, leaseUntil, expectedSlotRevision}` |
| `createRun(auth, snapshot, replaceActive=false)` | `{run, slotRevision}` |
| `readRun(runId)` | `{id, revision, status, snapshot}`, or `undefined` if absent |
| `saveRun(runId, auth, expectedRunRevision, snapshot)` | Updated run object directly |
| `readProfile()` | Canonical pure profile directly, not a storage envelope |
| `readReceipt(runId)` | Canonical receipt directly, or `undefined` if absent |
| `settleRun(runId, auth, expectedRunRevision, outcome)` | Pure `{ok,status,reason,profile,receipt,new_unlocks}`, with `slotRevision` only on newly applied commit |
| `close()` | Synchronous `undefined` |

An auth object is `{owner,fence,expectedSlotRevision}` (returned `leaseUntil` is
informational). Run `revision` is a separate CAS argument. After create/settle the
caller updates its expected slot revision from the returned value; after save it
updates the run revision. A read is not permission to renew/reclaim a stale fence.
`duplicate` and `conflict` settlements do not advance revisions. A conflict is a
resolved pure result with `ok:false`, not a successful new commit.

The native prototype currently wraps values, such as `{ok,auth}` or `{ok,run}`.
These are **not wire-compatible return shapes** with this JS API. An eventual
JavaScriptBridge/native adapter must map both into an explicitly tested common
response format; neither implementation is a drop-in substitute today.
